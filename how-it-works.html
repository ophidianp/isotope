Read the game. Rewrite the mod.

Since 26.1, Minecraft ships with real names in its code. That means the difference between two releases can be read straight off the game itself, and a mod can be pointed at the new names.

Most of the game stays put. Some of it moves.

Isotope's table generator compares two game jars. Anything in the old one but not the new one is "missing", and it tries to prove where each missing thing went.

Only confident matches become rules.

A wrong rule would quietly call the wrong method, which is worse than a clear "missing" in the report. So the matcher stays strict, and anything it cannot prove is reported instead.

  • Classes (moved). A moved class keeps its methods, so it is matched by its member list. 26.3 moved most of com.mojang.blaze3d to com.mojang.renderpearl.
  • Methods (renamed). A renamed method keeps its body, so the code inside is compared. PoseStack.mulPose became rotate.
  • Fields (renamed). Matched by how they are set up (registry names survive a rename) or by which methods use them.
  • Signatures (re-signed). When a parameter became a parent type or a method started returning a value, the call is re-pointed and adjusted so the mod never notices.
  • Mixins and access wideners (strings). Mixins name their targets as text, like "Lnet/minecraft/...;getX()D". Those strings are rewritten too, along with access-widener lines.

When a machine can't prove it, a person checks it.

A few changes can't be matched automatically. Those get hand-written rules, each verified against both game jars and explained next to the rule. Two kinds exist so far:

PushReaction.DESTROY  →  POPPED       201 of 201 blocks agree
PushReaction.BLOCK    →  IMMOVEABLE   11 of 11 blocks agree
simpleCodec(...)      →  null         codecs were removed in 26.3

The first kind is a rename proven by usage: 26.3 renamed and reordered every PushReaction value, so matching by position would have been wrong. The second is a stub: 26.3 removed block codecs entirely, but old mods still build one when they load, so they get null instead of crashing. Stubs are only used when the game no longer reads the value at all.

When the game changed shape, not just names.

Testing real mods showed where renames are not enough. Each of these fixes came from a real failure, and each is checked against Mojang's own game before it ships.

  • Data files are converted. 26.3 changed the format of loot tables, advancements and world-gen data. Isotope converts a mod's files; run over Mojang's own 26.2 files, the result matches Mojang's 26.3 files for 99.7% of loot tables and 99.3% of advancements.
  • One bad method no longer sinks a class. Java rejects a whole class if one method needs something that is gone. Isotope runs Java's own check first and replaces only that method, so the rest of the class still works.
  • Classes that became interfaces. Mojang turned structure processors, placements and placement modifiers into interfaces that hand out their codec directly. Isotope reshapes the mod's classes to match and bridges the old "type" objects.
  • Colored blocks became collections. 26.2 replaced 460 fields like WHITE_WOOL with collections like WOOL.white(). Isotope rewrites every use, after confirming each entry is the very same block.

Resolve everything. Before Java has to.

Java links lazily: a missing method only throws when that line runs, maybe an hour into play. Isotope does the same lookups up front, for every instruction, and writes the result to isotope/report.txt.

Some crashes are certain. Those mods stay out.

A mod that would crash on every launch is held back by default, along with anything that needs it. Set load-mods-with-fatal-problems=true to try anyway.

  • Class changed shape (fatal). The mod extends a game class that has since become final, sealed or an interface. Java refuses to load that class at all. 26.3 sealed Holder and turned Feature into an interface.
  • Fails at startup (fatal). Isotope follows the mod's own code from its initializer. If something on that path no longer exists, the crash happens on every launch, so it is not a "maybe".
  • Everything else is reported (reported). A missing method in a rarely used corner may never run. Those mods load, and the report lists where they could fail.
  • Mixins that miss are skipped (lenient). By default, a hook that no longer fits is skipped with a log line instead of crashing. The feature behind it won't work.
